# Known failure modes

Part of the `build-throne-win64` skill. Level: project.

## Known Failure Modes

These problems were already hit while making the installer reproducible:

- A portable pre-build can legitimately show the old Windows resource value such as `0.1.8.0`; do not mistake it for the requested release. For a patch release from `VERSION.txt` `0.1.8`, run the installer workflow and require `VERSION.txt`, `NKR_VERSION`, the installer filename, and the GitHub tag to resolve to `0.1.9` before publishing.
- Do not use repo-local `build-local`; it is intentionally not part of the workflow. Use `%LOCALAPPDATA%\CodexBuild\AmneThron-win64`.
- CMake must use `-G Ninja`. The Visual Studio/MSBuild generator previously selected an unsuitable Debug-style build path and hit third-party warning-as-error failures.
- Qt Network configuration needs explicit local OpenSSL paths from `.tools\openssl-x64\openssl`; otherwise `WrapOpenSSL::WrapOpenSSL target was not found`.
- `srslist.h` is not tracked and is ignored by the repo. Download it into the build directory before CMake, as Throne CI does.
- Current upstream `srslist.h` exports `ruleSetList`, not the old `ruleSetMap`. The compatibility map lives in `include/configs/rule_set_catalog.hpp`.
- Do not include `srslist.h` or `rule_set_catalog.hpp` from broad global headers such as `include/global/Configs.hpp`. It forces many translation units to parse a huge generated list and can turn installer packaging into a long rebuild.
- Download `srslist.h` to a temp file and replace the existing build copy only when the hash changes. Rewriting it every run invalidates CMake/Ninja dependencies and causes unnecessary rebuilds.
- Native commands such as `curl.exe`, `cmd.exe /c`, and `makensis.exe` can write progress or banner text to stderr. With `$ErrorActionPreference = 'Stop'` and redirected output, PowerShell can treat that as a terminating error before `$LASTEXITCODE` is checked. Temporarily set `ErrorActionPreference` to `Continue` around native commands and decide success from exit code.
- The skill wrapper must call the repo installer script with hashtable splatting, not positional array splatting, so `-Configuration` cannot be misread as the value for `-Increment`.
- NSIS relative paths are not reliably rooted at the repository. Missing `res\Throne.ico` was caused by path resolution. Use `${PROJECT_ROOT}\res\...` and `${PROJECT_ROOT}\deployment\...`.
- Missing `windowslegacy-amd64`, `windows-arm64`, and `windowslegacy-386` directories caused `makensis` file-not-found errors. The current installer intentionally aborts on non-AMD64 instead of packaging absent artifacts.
- If CMake/Ninja fails during regeneration with `ninja: error: failed recompaction: Permission denied`, a previous timed-out or interrupted build may have left `ninja.exe`, `cmake.exe`, `cl.exe`, `link.exe`, or `msbuild.exe` holding the external build cache. Check them with `Get-Process ninja,cmake,cl,link,msbuild -ErrorAction SilentlyContinue`, stop only those build processes when they are stale, then rerun the build.
- If `curl` cannot download `srslist.h` because GitHub is temporarily blocked, reset, or timed out, use the cached non-empty `%LOCALAPPDATA%\CodexBuild\AmneThron-win64\srslist.h` instead of failing the build. Both the skill build script and `script\build_windows_installer.ps1` should keep this fallback.
- Installer builds that bump `AMNETHRON_VERSION` can trigger a full rebuild and exceed a 20-minute shell timeout. The timeout may kill the PowerShell wrapper while orphaned `cmake.exe`/`ninja.exe`/`cl.exe` continue compiling, so do not launch a second build immediately. Monitor with `Get-Process cmake,ninja,cl,link,makensis -ErrorAction SilentlyContinue`; after `cmake`/`ninja` finish, if no `deployment\installer\ThroneSetup-<version>.exe` was produced, rerun `build-installer.ps1 -StopExisting`. The second run should be `ninja: no work to do` and proceed to NSIS packaging.
- If GitHub publication reports that the tracked worktree is dirty, commit the matching source and `VERSION.txt`, push the commit, then rerun only `publish-github-release.ps1`; do not rebuild and consume another version.
- On Windows PowerShell 5.1, passing Russian release JSON to `Invoke-RestMethod` as a .NET string can make GitHub return `400 Problems parsing JSON`. Encode serialized JSON as explicit UTF-8 bytes with `application/json; charset=utf-8`. Keep `-ValidateOnly` exercising this JSON POST path through GitHub's non-persistent Markdown renderer before creating a release. After this publication-only fix, commit and push the script, then retry publication without rebuilding or consuming another version.
- PowerShell parses `"$uploadUrl?name=$encodedName"` as the variable `$uploadUrl?name`, producing an invalid URI such as `=ThroneSetup-<version>.exe`. Build the upload URI in a helper using `"${uploadBase}?name=..."`, validate it with `Uri.IsWellFormedUriString`, and exercise that helper in `-ValidateOnly`. If the release was already created with no asset, commit and push the publisher-only fix and rerun publication; update the existing release and upload the asset without rebuilding or incrementing the version.
- A large public release-asset download can repeatedly fail with `curl: (35) Recv failure: Connection was reset` even after GitHub accepted the upload. Do not rebuild or replace the asset solely because this verification download failed. Verify the GitHub asset response/API instead: `state` must be `uploaded`, `size` must equal the local file size, and `digest` (when present) must equal `sha256:<local SHA-256>`. Keep these checks in the publisher immediately after upload; prefer the server digest over repeatedly downloading the same large file through an unstable CDN path.
- If GitHub authentication is missing, sign in through Git Credential Manager or set `GH_TOKEN`/`GITHUB_TOKEN`; never print or persist the token in build logs or files.
- If an asset with the same version already exists, the publisher replaces that asset and updates the release body instead of creating a duplicate release.
